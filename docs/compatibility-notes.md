# Compatibility notes / 兼容性核查记录

## Support matrix

Requires DeepSeek Harness **`0.1.5-alpha.1` or later** (the `0.1.5`–`0.2.1` kernel release lines; peer ranges `@deepseek-ai/dsh-api-remotes@^0.1.5-alpha.1 || ^0.1.6-alpha.1 || ^0.1.7-alpha.1 || ^0.1.7-rc.1 || ^0.2.0-rc.1 || ^0.2.0-rc.2 || ^0.2.1-alpha.1`, `@deepseek-ai/dsh-settings@^0.1.5-alpha.1 || ^0.1.6-alpha.1 || ^0.1.7-alpha.1 || ^0.1.7-rc.1 || ^0.2.0-rc.1 || ^0.2.0-rc.2 || ^0.2.1-alpha.1`, `@deepseek-ai/schemastery@^3.18.0 || ^3.18.5-alpha.1`). The peer range is a per-line union rather than `>=0.1.5-alpha.1` because semver's prerelease exemption only covers the same `major.minor.patch` tuple — a `>=0.1.5-alpha.1` range matches no later prerelease line.

> **On an older DeepSeek Harness?** This release line targets `0.1.5-alpha` and later — the `0.1.2-rc` / `0.1.3-alpha` lines and earlier are **no longer supported**. Please upgrade Harness, or install an older plugin release that matches your kernel (for example `dsh-better-reasoning-effort@0.3.7` for the `0.1.2-rc` / `0.1.3-alpha` lines).

Compiled and gated against `0.2.0-rc.2` and `0.2.1-alpha.2` (typecheck, the test suite and the full build all run against each line's official packages; the dev dependencies track the published `0.2.1-alpha.2` line). The most recent **live-kernel** runtime verification covers both lines — an isolated-instance pass on `0.2.1-alpha.2` and on `0.2.0-rc.2` (see the live re-check section below); before it, the last pass was `0.1.7-rc.2`.

## 0.1.5-rc.2 → 0.1.6-alpha.1

Seam-by-seam source re-check: the settings service (`get` / `describe` / `update` plus `settings/updated`) and the generated Typert `ctx.remote.settings` contract, the two `settings.models` slot seats, the slots / locale runtime, the `connection` service and its `connection/reset` event, the six Models-page anchor aria-labels and the structural class names, the composer model popover (`aria-controls` → `role="menu"` → `menuitem` / `menuitemradio`), the `dsh.client` load rules and the `/plugins/<id>/client.js` route, the `llm` service wrappers (`prepareCall` / `stream`) and `webServer.register`, and pi-ai's `config.ts` / `catalog.ts` (compat keys, `reasoningEfforts`, `input`) — every carrying implementation is unchanged. Two neighbouring edits stay off this plugin's injection path: `ui-settings-models` gained a placeholder and hint copy for deepseek-family endpoints, and `ui-input-trigger` changed how slash-command menu rows render (this plugin injects into the `ModelSelect` popover). The `0.1.5`-line compatibility notes still hold (verified source-level: the settings Remote wire, the Models-page anchors, the model-directory types, slots / locale are unchanged since `0.1.2-rc.1`; only the `llm-pi-ai` compat schema grew — pi-ai 0.85.1 adds `thinkingTokenBudgetField` / `vllmPriority` / `supportsMaxOutputTokens` — and the composer model menu is now portaled to `document.body`, which the slider follows through the trigger's `aria-controls` link with the inline shape kept as fallback). New-schema keys are suggested where the protocol takes them and stripped automatically on a write refusal from an older kernel, with no version sniffing. Seam details: the settings Remote is the generated Typert `ctx.remote.settings` stub (argument-less `describe`, positional `mutate(ns, ops, expectedRevision)`, `{ok, value | error}` envelopes, `settings/conflict` / `settings/rejected` refusal codes), the Models-page anchors (`Capacities`/容量, Model ID, Display name, Provider ID, Base URL, API protocol; the `settings.models.footer` slot) are unchanged, and the raw-listing probe mirrors the kernel's own model discovery — the same protocol set (now including **Anthropic Messages** via its native `/v1/models` route with `x-api-key` + `anthropic-version`), the same dual `data`/`models` listing shapes, and the same 4 MB ceiling. The client bundle requests no official module at runtime, so it loads unchanged.

## 0.1.6-alpha.1 → 0.1.6-alpha.2

A further source re-check found exactly two carrying changes, both now adapted **without version sniffing**: the sessions list snapshot dropped its `current` selection (navigation moved to the view owner), so the composer slider resolves the current session from `ctx.uiSession`'s main-view binding, falls back to the first main-view-retained catalog row, and still reads `current` on older kernels; and `ModelDirectory.select` now RESOLVES a `{ok:false}` refusal result instead of throwing, which the effort-memory and slider commit paths normalize alongside the thrown shape. The Models-page disclosure label was renamed from `Capacities`/`容量` to `Model options`/`模型选项`; the injector anchors by the `modelAdvanced` dictionary key and follows it automatically, with `Capacities` kept as the no-dictionary fallback. `0.1.6-alpha.2` also added an official per-row Input-types editor (`ModelInputTypes`), which this plugin treats as a capability: the injector sniffs that control in each row's disclosure DOM and hides its own modality section on exactly those rows, so one modality surface remains (older kernels keep the plugin's). Everything else — the settings Remote, the slot seats, the composer menu DOM, the pi-ai schema, the `llm` wrappers and `webServer.register` — is unchanged.

## 0.1.7-alpha.1

`0.1.7-alpha.1` replaces the settings provider's `get` / `installSection` shape with `SettingsForms`. The host half now reads the `llm-pi-ai` descriptor's resolved `value` and caches it until `settings/document-updated` invalidation; the browser half prefers `ctx.configForms.get('llm-pi-ai')`, then falls back to the older `ctx.settingsScope.bind({ namespace })`, then to `remote.settings.describe()`. The pi-ai configuration vocabulary (`providers`, `reasoningEfforts`, `input`) and the per-model DOM anchors (`modelAdvanced`, `modelInputTypes`) are unchanged. The Models-page add flow was reorganized, but it stays outside the per-row injection path.

## 0.1.7-rc.2 (live re-check, 2026-09)

**`0.1.7-rc.2` live re-check** (the release this plugin's request-header work was verified end-to-end on): three facts differ from the older `0.1.5-rc.2` test baseline and affect **manual/scripted verification**, not the plugin, so they are recorded here to save the next person the detour — (1) `settings.yaml` is retired: the kernel renames it to `settings.yaml.imported` at boot and imports each section into the profile's patch file, `profiles/<name>/cordis.patch.yml` (the settings service's `documentPath`), so "what the user wrote" lives in the patch file; (2) `settings/describe` no longer accepts a `_request` argument (passing one is refused as `gateway/arguments-invalid`), while calls like `session/page` still take `request` — the argument field differs per method, so measure rather than assume; (3) the theme tokens (`--dsw-alias-*`) live on `<body>`, not `:root`, and the palette switches through `html[data-ds-theme-source]` plus `color-scheme`, so reading a token at runtime means reading it from `document.body`. Evidence from that run: the request-header section rendered inside the provider card and repainted correctly across language and theme, a UI save landed `headers.x-company` and `headers.user-agent` in the patch file, and the host's overlay index went from empty to `{origin: http://127.0.0.1:<port>, route, userAgent}` on the live settings event.

A second isolated-instance pass on `0.1.7-rc.2` (2026-09, the slider commit fix) additionally confirmed: `npm view` publishes the `0.1.7-rc.1`/`rc.2` line the peer ranges now name; `settings/describe` still refuses `_request` (see above); the seeded third-party route and its `reasoningEfforts` declaration flow through the composer model menu unchanged.

## 0.1.7-rc.2 → 0.2.0-rc.1

The plugin loader (`boot/plugin-manager`) and the bundle composer's patch format are unchanged (the official bundle roster merely swaps rows). `vendor/cordis` (4.0.4) and `vendor/schemastery` (3.18.4) are identical on both tags. Adaptation is therefore declarations only: the peer ranges gain `|| ^0.2.0-rc.1` and the dev dependencies move to the `0.2.0-rc.1` line. Verified against the published `0.2.0-rc.1` packages: typecheck clean, the full suite 454/454, and the full build green. No live-kernel pass on `0.2.0-rc.1` yet; the most recent one remains `0.1.7-rc.2`.

## 0.2.0-rc.1 → 0.2.0-rc.2

A seam-by-seam diff of the same ten packages: `dsh-settings`, `dsh-client-locale`, `dsh-client-store`, `ui-settings`, `ui-slots`, `dsh-host-webserver` and `dsh-api-session-controller` are source-identical (version bumps only); `dsh-api-remotes` only mounts a new `user-questions` remote behind an unchanged export surface; `ui-primitives` added the `MenuGroup` / `observeStickyMenuGroups` pair and turned `Input` into a `forwardRef`, none of which this plugin imports. Two changes carry, both in `ui-model-selection`: the model list pane swaps its popover's role from `menu` to `group` — its own list box takes `role="menu"` (ModelSelect.tsx:484) — and the pane grows an official search box above four models. The role swap broke `findModelMenu()` (a `role="menu"`-only probe lost the popover for as long as the user browsed models), so the finder now judges the popover by its role AND its menu rows: `group` passes only when it carries a `menuitem` / `menuitemradio` row, and the sibling fallback widens the same way. The official search box retires this plugin's own composer search box, its styles, its copy keys and its spec; the composer injection now only owns the slider, its pane probe is the `menuitemradio` marker it already used for the replica retire/restore, and the same-frame re-place runs on a drill-in change alone. The `MenuGroup` sections keep `section[role="group"]`, but no plugin probe reads them any more. One seam is now DRIVEN rather than sniffed: on rows whose official Input-types fieldset owns modalities (0.1.6-alpha.2 onward) the plugin's own section stands down, so Auto-adapt clicks the official checkbox its suggestion disagrees with — the fieldset renders `['text', 'image']` in that order and carries no value/name to match on (ModelInputTypes.tsx:39), so the boxes are matched by position, and a missing control, an unexpected box count or a disabled box leaves the page untouched. The `0.1.7-rc.2` sidebar / `ui-input-trigger` notes still hold; nothing else on this plugin's path moved.

`llm-pi-ai` keeps the same three route protocols (`PROTOCOLS`, provider.ts:47) and the same listable set (discovery.ts:38), so the inference vocabulary is unchanged: pi-ai `^0.85.1 → ^0.87.1` only reshapes its compat gates (drops `deferredToolsMode` and `supportsToolReferences`, adds `supportsMidConvo*` and `sessionAffinityFormat`, and a `mistral-conversations` gate no route can name — `supportedProtocols()` is still the three-value `PROTOCOLS` table). Every compat field this plugin offers or writes — `thinkingTokenBudgetField`, `supportsThinkingTokenBudget`, `vllmPriority`, `supportsMaxOutputTokens`, `supportsDeveloperRole`, `forceAdaptiveThinking` — is still classified `'offer'` (catalog.ts:234/246-248/264-265/282), and `sanitizeCompatForProtocol()` keeps pruning by whitelist, so no new gate field can reach a write.

Verified against the published `0.2.0-rc.2` packages: typecheck clean, the full suite 441/441, and the full build green. No live-kernel pass on `0.2.0-rc.2` yet; the most recent one remains `0.1.7-rc.2`.

## 0.2.0-rc.2 → 0.2.1-alpha.2

A seam-by-seam diff of the packages this plugin binds to found **no carrying change** to the injection or write path. `dsh-settings`, `dsh-client-store`, `dsh-client-ui-slots` and `dsh-api-remotes` are source-identical apart from version bumps and READMEs. `dsh-host-webserver`'s 324-line delta is TLS configuration plus a bind-address tightening that forbids wildcard binds (`isWildcardHost` / `normalizeBindAddress`) — the `register({ kind: 'exact', path, handler })` surface is untouched, and a concrete interface literal still arrives at the plugin's trust fence as an IP literal. `ui-settings-models` changed only its load / `status` handling (`hasReadySnapshot`, buttons disabled while a refresh is in flight): no DOM anchor, aria-label or slot name moved — `ModelsSection.module.css` still carries the `.editor` class root the provider-card edit-state probe keys on, `settings.models.provider-card` still receives `{ provider: row.entry, configured, keyConfigured }`, and `settings.models.footer` is unchanged. `ui-model-selection` replaced its internal `state.current` checks with the selected `currentChoice` and reworded one Chinese string (`empty.models`); this plugin reads neither, and the slider's anchors stay `role="menuitem"` / `role="menuitemradio"`. In `llm-pi-ai`, `catalog.ts` gains `servesChat()` (a catalog provider whose catalog lists only non-chat models stops being a catalog route) while `modelOverrides`, its four validation rules and the `resolveRouteModels` merge are unchanged; `adapter.ts`'s edits are an Anthropic deferred-tool placeholder and a stream-teardown change, and `reasoningEfforts` → `thinkingLevelMap` is unchanged. pi-ai moves `^0.87.1 → ^1.0.2` (resolved 1.2.0): every `thinkingFormat` this plugin writes (`openai`, `deepseek`, `qwen`, `zai`) and the three aggregator formats it now prefers (`openrouter`, `together`, `baseten`) resolve to the same dispatch branches as in 0.87.1 — verified by unpacking both releases — and `THINKING_FORMAT_GATE` is identical between the two tags.

Adaptation is declarations plus one knowledge-base behavior change: the peer ranges gain `|| ^0.2.1-alpha.1`, `@deepseek-ai/schemastery` gains `|| ^3.18.5-alpha.1`, and the dev dependencies move to the `0.2.1-alpha.2` line (`schemastery@3.18.5-alpha.1`, `cordis@4.0.4`); separately, an aggregator's own `thinkingFormat` now outranks the model family's, so a model served through OpenRouter / Together / Baseten names the dialect that gateway actually reads instead of its vendor's own field. Verified against the published packages on **both** lines: typecheck clean, the full suite **469/469** and the full build green on `0.2.0-rc.2` (pi-ai 0.87.1, schemastery 3.18.3) and on `0.2.1-alpha.2` (pi-ai 1.2.0, schemastery 3.18.5-alpha.1). Both lines also passed a live isolated-instance check — see below.

## 0.2.1-alpha.2 → 0.2.1-rc.2

`0.2.1-alpha.4` adds an official **Reasoning levels** editor for models of a hand-declared pi-ai route (`ui-settings-models`'s `ModelReasoningEfforts`: a switch plus one level / API-value row each). It renders inside the same per-row `modelAdvanced` disclosure this plugin injects into, after `ModelInputTypes` (`ModelRow.tsx:112-118`), so the plugin reads that block's `modelReasoning` class-name stem as a CAPABILITY — the same rule as the input-types fieldset — and stands its own ladder down on exactly those rows. The level checkboxes and wire inputs disappear; the default-effort pick, the endpoint-compatibility controls and Auto-adapt stay, and every write the editor makes then carries `efforts: 'keep'`, so a default-pick or compat edit cannot overwrite the official declaration. Auto-adapt still consults the knowledge base and still carries compat and modalities (driving the official input-types checkboxes when that control owns them), but reports its suggested ladder as text (`officialLevelsSuggest`) instead of writing `reasoningEfforts`; a suggestion carrying neither compat nor modalities writes nothing. Rows without the official block (installed-catalog routes, older kernels) are unchanged. Source-level check against the `0.2.1-rc.2` tree; the suite covers the sniff, the stand-down and the `'keep'` writes.

## Live re-check on 0.2.0-rc.2 and 0.2.1-alpha.2 (2026-10)

Two isolated instances, each with its own `DSH_HOME` and a seeded fake provider (`local-test`, `baseURL: http://127.0.0.1:9/v1`, a discard port so no call can leave the machine) plus a seeded session: one on `0.2.1-alpha.2` (the npm global `@deepseek-ai/dsh`, whose bundled kernel packages are all `0.2.1-alpha.2` and which carries `cordis@4.0.5-alpha.1`) and one on `0.2.0-rc.2` (the desktop runtime). The plugin was installed as a packed tarball in both; the kernel actually in use was confirmed from the listening process's command line and from the status route's `adapterPath`, **not** from `dsh -V` — a PATH `dsh` and `npx @deepseek-ai/dsh@<version>` can resolve to different installations.

On both lines: the plugin loaded; `/dsh-better-reasoning-effort/headers-config` answered 200 carrying the new `guard` report (`{"enabled":true,"installed":true,"inspected":0,"injected":0}`); the raw-listing probe reached the seeded route and reported the discard endpoint's connection failure rather than an unknown route; and automatic fill wrote `reasoningEfforts` **and** `compat.thinkingFormat: "openrouter"` for `deepseek-chat` on a route whose `baseURL` is `https://openrouter.ai/api/v1` — the aggregator's dialect, where that model's family dialect is `deepseek`. The control model absent from the knowledge base (`test-model`) stayed unfilled on both, and the fill persisted to the profile's `cordis.patch.yml`.

Known issue this pass found, present on both lines and independent of the changes above: on a boot that has to import a settings file, the host-side automatic fill is skipped **silently** when the `llm-pi-ai` namespace registers later than the boot retry window (about 61 seconds over `[1s,2s,4s,8s,16s,30s]`). It filled within seconds of a restart, and the browser half's idle fill covers it once a page is open — but a headless deployment that imports a settings file and never opens a page can be left with unfilled declarations.

Neither line has had a live pass over the request-header editor's write path (a UI save landing `headers.*`) or over the composer slider's drag-and-commit; both remain covered by the suite alone.

## One DOM-bypass path for the per-model editor (no version sniffing)

The injector keys off the official disclosure anchors by the `modelAdvanced` dictionary value (`Capacities`/`容量` on the `0.1.6-alpha.1` line, `Model options`/`模型选项` from `0.1.6-alpha.2`), so the editor mounts under every model row that expands — inside the *edit → custom settings* flow — including unsaved rows on a provider's create card (staged, flushed the moment the row is saved). The slider toggle rides the official `settings.models.footer` slot, declared through the plugin's own `remote.settings` inject — the same service contract the official Models page consumes. The Models page's other sanctioned seat, the keyed `settings.models.provider-card` (per provider card), is where this plugin's **request-header editor** lives (see the README's Features) — `headers` is a provider-level fact; and no slot reaches a single model row, which is why the per-model editor keeps the DOM bypass.

## 0.1.5-rc.1 runtime re-check

Runtime re-check against the `0.1.5-rc.1` kernel (2026-09): the settings Remote's `describe` / `mutate(ns, ops, revision)` contract, the Models-page anchors, and the slider's menu discovery are unchanged; rc.1's two `llm-pi-ai` tightenings are covered here — a model-level compat key must belong to the protocol that model resolves to (the write path strips per protocol and retries, with the refusal prose pinned verbatim in a test), and stored profiles that no longer validate surface as a row-level error on the provider card instead of failing the whole page.
